# BLUEPRINT 1.8 — Presentación Astro (Checkpoint 2: primera guía real)

> Define cómo se conecta el motor de dominio (1.7.1/1.7.2, ya cerrado en el Checkpoint 1) con Astro para producir la primera página real: `/islandia/islandia-en-camper-13-dias/`.
>
> **Objetivo:** que Claude Code pueda implementar esta única página sin tomar decisiones de arquitectura adicionales, igual que 1.7.2 hizo posible el motor sin decisiones adicionales.
>
> Este Blueprint no generaliza todavía a rutas dinámicas, componentes reutilizables, selector de ritmo, mapa interactivo, PDF ni "Adapta este viaje". Eso es trabajo de checkpoints posteriores.

---

## 1. Principio de arquitectura

La cadena de dependencias del 1.7.1 se completa ahora con su segundo tramo:

```
CONTENT → LOAD → SCHEMAS → DOMAIN ENGINE → PRESENTATION (Astro)
```

En términos concretos de este checkpoint:

```
content/{places,guides}/*.yaml
        ↓ (en tiempo de build)
engine (load → validate → compile)
        ↓
CompiledGuide
        ↓
src/lib/engine-guide.ts   ← único punto de contacto entre src/ y engine/
        ↓
src/pages/islandia/islandia-en-camper-13-dias.astro
        ↓
HTML estático
```

**Prohibido** (además de lo ya prohibido por 1.7.1 §1):
- `Página/Layout/Componente Astro → engine/*` directamente.
- `engine-guide.ts → decisiones de negocio` (qué variante mostrar, cómo filtrar paradas, cálculos). Eso vive en el motor, nunca en el orquestador.

---

## 2. El conflicto de modelos descubierto al empezar este checkpoint

Antes de escribir código se encontró que el repositorio ya tenía un sistema de páginas de guía funcionando (`src/content/schema.ts`, `src/content.config.ts`, `src/pages/[destino]/[slug].astro`, `src/lib/guide.ts`), construido para la guía de Alsacia **con un modelo de datos distinto e incompatible** con el `CompiledGuide` de 1.7.2:

| | Sistema existente (Alsacia) | Motor de dominio (1.6/1.7.x) |
|---|---|---|
| Convención de campos | camelCase | snake_case |
| Eje de personalización | grupo (`couple/friends/family_seniors`) con `groupAdjustments` por día | ritmo (`intensivo/equilibrado/tranquilo`) con variantes completas |
| Variantes de días | `variants` indexado por número de días | variantes completas con sus propios días |
| Verificación | `source.checkedAt` opcional por parada | `place.verified_at` + `is_stale` derivado, `visit_status` por parada |

**Decisión:** no se adapta ni se generaliza ninguno de los dos sistemas para que acepten al otro. Se construye una **página nueva y separada** que lee `CompiledGuide` directamente, sin tocar `schema.ts`, `content.config.ts`, `[destino]/[slug].astro`, `lib/guide.ts` ni la guía de Alsacia. Los dos sistemas convivirán hasta que haya una decisión explícita de migrar o retirar el antiguo — esa decisión no se toma en este Blueprint.

## 3. `src/lib/engine-guide.ts` — único punto de contacto con el motor

**Regla dura:** ninguna página, layout ni componente Astro importa desde `engine/` o `schemas/` directamente. Todo pasa por este fichero. Si en el futuro cambia la implementación interna del motor, solo este fichero necesita cambiar.

`engine-guide.ts` es un **orquestador puro**: encadena `load → validate → compile` y devuelve el resultado o lanza. No decide nada, no calcula nada, no filtra nada. Cualquier lógica condicional pertenece al motor.

```ts
// src/lib/engine-guide.ts
import {
  loadGuide, loadPlaces, buildPlaceRegistry, validateGuide, compileGuide,
} from '../../engine/index.ts'
import type { CompiledGuide, AffiliateRegistry } from '../../engine/index.ts'

function emptyAffiliateRegistry(): AffiliateRegistry {
  return { get: () => undefined }
}

export async function loadCompiledGuide(guidePath: string, placesPath: string): Promise<CompiledGuide> {
  const rawPlaces = await loadPlaces(placesPath) as unknown[]
  const { registry: places, errors: placeErrors } = buildPlaceRegistry(rawPlaces)
  if (placeErrors.length > 0) {
    throw new Error(`Errores en el registro de lugares (${placesPath}):\n${placeErrors.join('\n')}`)
  }

  const rawGuide = await loadGuide(guidePath)
  const affiliates = emptyAffiliateRegistry()
  const result = validateGuide(rawGuide, places, affiliates)

  if (result.errors.length > 0) {
    throw new Error(`La guía "${guidePath}" no pasa la validación:\n${result.errors.join('\n')}`)
  }
  for (const warning of result.warnings) {
    console.warn(`[${guidePath}] ${warning}`)
  }

  return compileGuide(result.guide!, places, affiliates)
}
```

`placeMapUrl` (§7) **no vive aquí** — no es parte de `load → validate → compile`, es una utilidad de presentación sin relación con el motor. Va en `src/lib/maps.ts`, separado:

```ts
// src/lib/maps.ts

/** A single "ver en Maps" link per stop — never a multi-waypoint day route (Google Maps caps waypoints around 9-10, and several Islandia days exceed that). */
export function placeMapUrl(lat: number, lng: number): string {
  return `https://www.google.com/maps/search/?api=1&query=${lat},${lng}`
}
```

El path de la guía y de los lugares (`content/guides/islandia/islandia-en-camper-13-dias.yaml`, `content/places/islandia.yaml`) se resuelven relativos a la raíz del repo, igual que ya hace `scripts/validate-content.ts`.

**Sobre `emptyAffiliateRegistry()`:** es temporal, igual que en `scripts/validate-content.ts` — existe porque `data/affiliates.yaml` todavía no existe (1.7.1 §5, diferido a antes de Fase 4). Su `get()` devuelve siempre `undefined`, lo que significa que **cualquier `affiliate_id` referenciado en la guía de Islandia hace fallar la validación** (`[ERROR] affiliate_id inexistente`, ver `engine/validate/references.ts`) y por tanto el build — no se resuelve nunca en silencio como `undefined` en el `CompiledGuide`. Esto es correcto y deliberado: la guía de Islandia no tiene ninguna referencia a afiliados (decisión ya tomada en el Checkpoint 1), así que este registro vacío no debería activarse nunca en la práctica; si algún día se añade un `affiliate_id` a esta guía sin haber creado el registro real, el build debe fallar, y así lo hace.

## 5. Contenido de la página, en orden

Todas las secciones leen directamente de `CompiledGuide` (via `engine-guide.ts`), reutilizando `BaseLayout.astro` tal cual (ya resuelve `<title>`, `description`, `canonical`, OG/Twitter, `noindex`).

1. **Cabecera**: título; dateline — "Lo hicimos en {trip_done}" si `has_experience`, si no "Actualizado {updated_at}".
2. **Caja de resumen**: `summary` (tagline, `best_season`, `getting_around`, `base_area`, `budget_per_person` si existe).
3. **Itinerario día a día**: como solo hay una variante (`intensivo`), se listan sus días directamente — **sin selector**. Por día: título, resumen, paradas (orden, duración, hora si existe). Ver §6 para los badges de verificación y §7 para los enlaces de mapa. Por parada: `variant_note` si existe. Por día: `our_take`, `plan_b`.
4. **Dónde dormir** (`accommodation.zones`, con `picks`).
5. **Cómo llegar** (`transport.arrival`, `transport.local`).
6. **Presupuesto real** (`budget`: `items`, `total_reference`, `currency`, `includes`/`excludes`). **Se muestra `total_reference`, nunca `total_base`** — confirmado en `engine/types.ts` y en 1.7.2 §5: `total_reference` es "el total para el grupo de referencia" (aplica `basis` con `base_travelers`, para los 2 viajeros reales de esta guía). `total_base` es solo una suma simple sin aplicar `basis`, referencia editorial interna del autor, no un dato para mostrar al lector.
7. **Qué reservar y cuándo** (`booking_checklist`).
8. **Nuestro criterio** (`our_criteria`) y **Errores y trampas** (`pitfalls` + `terrain_tips`).
9. **Lo práctico** (`practical`: `documents`, `plugs`, `apps`).
10. **FAQ** (`faq`) — ver §8 sobre qué entra en los datos estructurados.

**Explícitamente fuera de este checkpoint** (F1 mínima, ver BRIEF §11 y roadmap del Checkpoint 1): selector de ritmo/grupo, mapa interactivo (isla Vue), botón de descarga de PDF, CTA "Adapta este viaje", cualquier formulario.

## 6. Verificación — versión básica

La promesa de marca ("Comprobado", "Vivido") entra desde este checkpoint, en su versión mínima que ya permite el modelo compilado:

- Cada parada con `visit_status: 'visited'` lleva una marca visual discreta (p. ej. una etiqueta "Vivido"). `not_visited` y `unknown` no llevan marca (nunca se presentan como vividos — I14).
- Cada parada muestra la fecha de verificación del lugar (`stop.place.verified_at`).
- Si `stop.place.is_stale` es `true`, se muestra un aviso discreto (p. ej. "dato de {verified_at}, puede haber cambiado") en lugar de silenciarlo. Esto es la traducción visual de los `[WARNING]` de datos caducados que ya emite el motor (1.7.1 §18).

No se construye todavía un sistema genérico de badges reutilizable entre páginas — esta es la primera vez que se renderiza, y generalizar antes de tener una segunda página real sería anticipar (regla de arquitectura de CLAUDE.md).

---

## 7. Enlaces de mapa — uno por parada, nunca por día

**Decisión corregida durante el diseño:** no se genera un enlace de ruta por día con todas las paradas como waypoints. Google Maps Directions limita los waypoints a 9-10, y varios días de Islandia (p. ej. el día 11, con 8 paradas) están cerca de ese límite o lo superarían al combinarse con origen/destino.

En su lugar, cada parada individual lleva un enlace "Ver en Google Maps" a su coordenada exacta, vía `placeMapUrl(lat, lng)` de `src/lib/maps.ts` — sin límite de waypoints porque es un único punto, no una ruta.

## 8. Datos estructurados

- **`Article`**: `headline` (título), `description`, `dateModified` (`updated_at`).
- **`BreadcrumbList`**: Inicio › Islandia › título de la guía.
- **`FAQPage`**: solo con los elementos de `faq` cuyo campo `schema` sea `true`. El resto de preguntas se muestran igualmente en la sección visible de FAQ (§5.10) — el filtro es solo para los datos estructurados, no para el contenido visible.

```ts
const faqForSchema = guide.faq?.filter((item) => item.schema === true) ?? []
```

Fuera de este checkpoint: `TouristTrip`/`ItemList` para el itinerario (nice-to-have, no crítico para el cierre).

## 9. SEO técnico

- **`noindex: true`** en esta página mientras el contenido esté pendiente de revisión final por el autor (19 lugares con coordenadas/notas marcadas como "pendientes de confirmar", días 9-12 con duraciones estimadas, Skógafoss con el dato editorial ya corregido pero sin revisión humana completa del resto). Se retira cuando el autor dé el visto bueno.
- Canonical, OG/Twitter cards, `<meta viewport>`: ya cubiertos por `BaseLayout.astro`, sin cambios.
- `sitemap.xml`: `@astrojs/sitemap` **no detecta `noindex` automáticamente** — el filtro actual de `astro.config.mjs` es manual y solo mira el content collection antiguo. Para que esta página `noindex` no acabe en el sitemap hay que añadir su ruta exacta (`/islandia/islandia-en-camper-13-dias/`) a la exclusión, con una línea adicional en `excludedPaths` (o una lista separada para páginas fuera del content collection antiguo). Es un cambio de una línea en `astro.config.mjs`, no en el sistema de Alsacia — la config del sitemap es infraestructura compartida del sitio, no algo propio de esa guía.
- HTML estático, Lighthouse ≥ 95 — criterio ya vigente, no cambia.

## 11. Manejo de errores

Mismo contrato que el motor (1.7.1 §13):

- `[ERROR]` (de `validateGuide`, o de `buildPlaceRegistry`) → `loadCompiledGuide()` lanza → `astro build` falla con el mensaje exacto. No hay lógica adicional de recuperación: el build debe fallar, tal como exige CLAUDE.md ("si una guía no cumple el esquema, el build falla").
- `[WARNING]` → se imprime por consola durante el build (visible en el log de CI), no bloquea nada.

## 12. Testing

- `tests/lib/engine-guide.test.ts` (mismo estilo que el resto del proyecto, `node:test`):
  - caso feliz: `loadCompiledGuide()` con las rutas reales de Islandia devuelve un `CompiledGuide` válido.
  - caso que falla: se le pasa una guía con un `place_id` roto (fixture temporal o copia modificada) y se comprueba que lanza con un mensaje que menciona el error.
- `tests/lib/maps.test.ts`: `placeMapUrl(lat, lng)` genera la URL esperada con el formato `query=lat,lng` — trivial pero cubierto, sin excepciones al estilo TDD del resto del proyecto.
- La página Astro no tiene test de renderizado automatizado (no hay Playwright en el proyecto). Verificación: `npm run build` en verde + comprobación manual de Lighthouse ≥ 95 + revisión visual en desktop y móvil (ver criterio de cierre, §13).

## 13. Criterio de cierre del Checkpoint 2

> `npm run build` genera `/islandia/islandia-en-camper-13-dias/` a partir de `content/guides/islandia/islandia-en-camper-13-dias.yaml`, pasando por el motor de dominio real (sin datos hardcodeados en el componente), con **build en verde + Lighthouse ≥ 95 + revisión visual del autor en desktop y móvil**, sin tocar ningún fichero del sistema de guías de Alsacia.

La revisión visual (desktop y móvil) es explícita y obligatoria, no implícita en "Lighthouse ≥ 95" — Lighthouse no detecta que un texto se corte, que una tabla desborde en pantallas estrechas, o que el espaciado no funcione con contenido real más largo que el de prueba. Se revisa la página renderizada de verdad, en ambos anchos, antes de cerrar el checkpoint.

Y, igual que en el Checkpoint 1: **no se declara terminado por "la página existe"**, sino por cumplir ese criterio completo (build + Lighthouse + revisión visual) y por que el autor revise el resultado (código, página renderizada, Lighthouse) antes de decidir el siguiente paso — generalizar a más guías, o continuar con SEO de contenido/diseño según el roadmap acordado.
