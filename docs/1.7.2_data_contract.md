# BLUEPRINT 1.7.2 — Contrato de datos ejecutable

> Define el modelo de datos exacto que conecta el contenido editorial con todos los outputs.
> **Orden:** modelo conceptual primero, Zod y TypeScript después.
>
> Principio: el `CompiledGuide` es lo que consume la aplicación. El `GuideSource` es lo que escribe el autor. Nunca se mezclan.

---

## Decisión previa: referencia vs. materialización

**`CompiledStop` contiene `place` resuelto, no `place_id`.**

El `place_id` cumple su función en el compilador y desaparece del modelo compilado. El consumidor recibe el lugar completo y no necesita conocer el registro de lugares.

Consecuencia: si se necesita el id en runtime (enlace, analítica), se lee de `place.place_id`.

El mismo patrón se aplica a afiliados: `affiliate_id` en source → objeto `affiliate` resuelto en compiled.

Esto es consistente con I2 (la parada no duplica datos del lugar): en source, la parada tiene solo la referencia; en compiled, tiene el objeto completo. No hay duplicación porque en source no había datos del lugar.

**Tres totales distintos — nomenclatura exacta:**

| Campo | Tipo | Quién lo calcula | Qué representa |
|---|---|---|---|
| `budget.total_base` | number | Compilador (D) | Suma simple de `items[].amount` ignorando `basis`. Referencia editorial del autor. |
| `budget.total_reference` | number | Compilador (D) | Coste calculado para `guide.base_travelers` aplicando `basis`. Es el total "para el grupo de referencia". |
| `summary.budget_per_person` | number | Compilador (D) | `total_reference / base_travelers`. Lo que aparece en la caja de resumen. |
| `total_for_user` | number | Motor de presupuesto en runtime | Calculado con `n_travelers` del usuario. **Nunca está en `CompiledGuide`.** |
| `per_person_for_user` | number | Motor de presupuesto en runtime | `total_for_user / n_travelers`. **Nunca está en `CompiledGuide`.** |

El compilador calcula los tres primeros. El motor de presupuesto calcula los dos últimos en tiempo de ejecución (Fase 4+). Esta separación evita que `CompiledGuide` tenga datos personalizados para un usuario concreto.

## 10. Reglas de compilación (el compilador las ejecuta en orden)

### Paso 1 — Cargar registros globales
Cargar `content/places/{destination}.yaml` → PlaceRegistry  
Cargar `data/affiliates.yaml` → AffiliateRegistry

### Paso 2 — Validar source (Zod)
Schema completo de `GuideSource`. Si falla → ERROR, detener.

### Paso 3 — Validar referencias
Para cada `place_id` en cualquier parada: existe en PlaceRegistry → si no → ERROR  
Para cada `affiliate_id` en cualquier booking/checklist/alojamiento: existe en AffiliateRegistry → si no → ERROR  
Para cada `affiliate_id` referenciado: `active: true` → si no → ERROR

### Paso 4 — Validar reglas de contenido
`experience{}` en parada con `visit_status != visited` → ERROR  
`status: draft` en build de producción → ERROR  
Primera persona en `LUGAR.notes` → WARNING  
Primera persona en `PARADA.variant_note` con `visit_status != visited` → WARNING  
`content_type: experience` sin `trip_done` → WARNING  
`verified_at` > `review_interval` en cualquier lugar → WARNING con lista de campos concretos

### Paso 5 — Compilar
Resolver `place_id` → objeto `CompiledPlace`  
Resolver `affiliate_id` → objeto `CompiledAffiliate`  
Calcular `n_stops` por día  
Calcular `n_stops_total` por variante  
Calcular `n_route_stops_total` por variante  
Calcular `all_places` por variante  
Calcular `budget.type`, `budget.verified_at`, `budget.total_base`, `budget.total_reference`  
Calcular `budget_delta.total` por variante  
Calcular `summary.budget_per_person` (`total_reference / guide.base_travelers`)  
Calcular `places` global de la guía  
Añadir `has_experience` y `compiled_at`

### Paso 6 — Resultado
Devolver `CompiledGuide` o lanzar los errores acumulados.

## 11. Motor de presupuesto (separado del compilador)

El compilador calcula `total_base` (suma simple) y `total_reference` (aplicando basis con base_travelers).  
El motor de presupuesto calcula el coste real según el número de viajeros:

```
para cada item:
  si basis = per_person:  coste = amount × n_travelers
  si basis = per_room:    coste = amount × ceil(n_travelers / travelers_per_room)
  si basis = per_group:   coste = amount

total = sum(costes_base) + sum(costes_delta_variante)
per_person = total / n_travelers
```

El motor de presupuesto es una función pura en `engine/budget/`. No es parte del compilador. Lo llama el compilador para `summary.budget_per_person` con los `base_travelers` de referencia de la guía, y lo llama el motor de adaptación con los `n_travelers` del usuario real.

## 14. Invariantes que deben probar los tests

Estos tests prueban que el compilador implementa correctamente los invariantes del modelo 1.6.

| Test | Invariante | Qué comprueba |
|---|---|---|
| `place_id inválido → ERROR` | I1, I5 | Un `place_id` no existente en el registry lanza error |
| `place en compiled ≠ place_id en source` | I2 | El compilado tiene objeto resuelto, no copia de datos |
| `places = unique(all stops)` | I3 | El campo `places` de la guía coincide con la unión única de lugares en todas las variantes |
| `total_base = sum(items.amount)` | I4 | Suma simple de amounts sin aplicar basis |
| `total_reference con 2 viajeros per_person 100€ = 200€` | I4 | El motor aplica basis correctamente |
| `affiliate_id inválido → ERROR` | I6 | Un `affiliate_id` inexistente lanza error |
| `entry.verified_at ≠ hours.verified_at` | I7 | Los dos campos se almacenan y recuperan de forma independiente |
| `adaptation_notes conservadas sin transformar` | I8 | El compilador no modifica el texto de las notas |
| `compiled_guide ≠ inventa datos` | I10 | El compilador no añade campos no declarados en source |
| `email no está en CompiledGuide` | I11 | El tipo `CompiledGuide` no incluye ningún campo de email de usuario |
| `CompiledGuide = fuente de web, PDF, maps` | I12 | El mismo objeto se puede pasar a distintos renderers |
| `basis declarado en cada item` | I13 | Ningún item puede carecer de `basis` |
| `experience en visited → OK` | I14 | `visit_status: visited` + `experience{}` = válido |
| `experience en not_visited → ERROR` | I14 | `visit_status: not_visited` + `experience{}` = error |
| `experience en unknown → ERROR` | I14 | `visit_status: unknown` + `experience{}` = error |
| `visit_status en PARADA, no en LUGAR` | I15 | `PlaceSource` no tiene `visit_status` |
| `actual_price_paid ≠ place.entry.price` | I16 | Los dos campos coexisten sin sobrescribirse |
| `budget.type derivado de items` | I4 | Si todos real → `real`; si todos estimado → `estimado`; si mezcla → `mixed` |
| `budget.verified_at = el más antiguo` | I7 | La fecha es la mínima de todos los `item.verified_at` |
| `n_stops_total = suma de n_stops por día` | I3 | El campo derivado coincide con el conteo real |
| `parking.price negativo → ERROR` | — | Enmienda C3: `price` ≥ 0 (0 = gratuito) |
| `parking caducado → stale_fields incluye parking` | I7 | `parking.verified_at` se evalúa con `review_interval`, igual que `entry` y `hours` |
| `price_checked_at` solo si el precio se comprobó antes de `updated_at` | — | Igual o posterior → ausente; sin parking → ausente |
| `day.photo sin alt → ERROR` | — | Enmienda C3: una foto de día sin `alt` (o con `alt` vacío) no valida |
| `day.drive no positivo → ERROR` | — | Enmienda C3: `km` o `minutes` ≤ 0 no validan |
| `route_line usa short_name ?? name` | — | Enmienda C3: la línea de ruta se deriva de `route_stops`, con `name` como respaldo |
| `campos de día conservados` | — | Enmienda C3: `photo`, `highlight`, `drive` y `overnight` llegan sin cambios al compilado |
| `status: draft bloquea en producción` | — | El validador de reglas de contenido lanza ERROR |
| `guía parcial (días 1-2, 9-12) = válida` | — | El schema acepta guías incompletas si cumplen los campos R |
