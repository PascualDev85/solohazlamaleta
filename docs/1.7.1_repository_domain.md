# BLUEPRINT 1.7.1 — Repository + Domain Architecture

> Define exactamente qué existe en el repositorio, qué responsabilidad tiene cada capa, cómo se relacionan y qué puede importar cada módulo.
>
> **Objetivo:** que Claude Code pueda implementar el esqueleto técnico sin tomar decisiones arquitectónicas adicionales.
>
> Este Blueprint no implementa todavía Astro, FastAPI, Supabase, PDF, mapas, pagos ni automatización.

---

## 1. Principio de arquitectura

La dirección de dependencias es estricta y nunca se invierte:

```
CONTENT → LOAD → SCHEMAS → DOMAIN ENGINE → PRESENTATION / APPLICATION
```

**Prohibido:**
- `Component → YAML`
- `Engine → Astro`
- `Engine → Vue`
- `Content → TypeScript`
- `Component → Supabase`
- `FastAPI → lógica de negocio propia`

---

## 2. Source model → Compiled model

### `GuideSource`
Representa exactamente lo que escribe el autor en YAML. No contiene campos derivados.

### `CompiledGuide`
Representa el modelo validado y preparado para consumo. Es el contrato común que consumen web, PDF, Maps, Mi viaje y email.

```
GuideSource → resolve → derive → CompiledGuide
```

El contrato exacto de `CompiledGuide` (qué campos conserva, transforma, añade y deriva) se define en **1.7.2**, que es el último paso conceptual antes de escribir código.

## 6. Islandia como fixture real

El primer YAML es contenido real del viaje, no el JSON conceptual del 1.6. Contiene **solo los días con `visit_status` confirmado**: 1, 2, 9, 10, 11 y 12.

Los días 3–8 **no aparecen**. No se rellenan con `visit_status: unknown` ni con datos inventados para simular una guía completa.

Esto prueba una propiedad importante del modelo: **acepta contenido parcial y honesto**.

Los tests usan directamente `content/guides/islandia/` y `content/places/islandia.yaml`. No hay copia artificial en `tests/fixtures/`. El viaje real es el regression test.

## 9. `engine/index.ts` — API pública (obligatorio desde el día 1)

```ts
// engine/index.ts
export { loadGuide, loadPlaces } from './load'
export { validateGuide } from './validate'
export { compileGuide } from './compile'
export type { GuideSource, CompiledGuide } from './types'
```

**Regla:** todo consumidor externo importa desde `engine`, nunca desde rutas internas:

```ts
// ✅ correcto
import { compileGuide } from '../engine'

// ❌ prohibido
import { something } from '../engine/compile/internal-file'
```

Si mañana cambia la implementación interna de `engine/compile/`, ningún consumidor externo necesita cambiar sus imports.

---

## 10. `engine/load/` — lectura sin lógica

Convierte YAML en objetos JavaScript/TypeScript sin aplicar ninguna regla de negocio.

```ts
loadGuide(path: string): Promise<unknown>
loadPlaces(path: string): Promise<unknown>
loadAffiliates(path: string): Promise<unknown>
```

El loader **no calcula, no resuelve derivados, no valida, no decide**. Solo lee.

---

## 11. `engine/validate/` — tres capas

### Capa 1 — Schema validation (Zod)
Estructura, tipos, enums, campos obligatorios, formatos.

### Capa 2 — Reference validation
```
place_id → existe en places registry
affiliate_id → existe en affiliates registry
```

### Capa 3 — Content rules
```
experience{} solo con visit_status: visited
status: draft bloquea en build de producción
primera persona en LUGAR.notes → warning
primera persona en PARADA.variant_note con visit_status != visited → warning
reviewed_at > review_interval → warning
```

---

## 12. `engine/compile/` — GuideSource → CompiledGuide

Transforma el modelo fuente en el modelo de consumo:

```
GuideSource + PlaceRegistry + AffiliateRegistry → compileGuide() → CompiledGuide
```

Aquí se resuelven referencias, se calculan los campos derivados (I3, I4) y se estructuran los datos para consumo. El contrato exacto se define en **1.7.2**.

---

## 13. Sistema de errores

### ERROR — bloquea build
```
place_id inexistente
affiliate_id inexistente
slug duplicado
campo R ausente
tipo incorrecto
experience{} en visit_status != visited
status: draft en build de producción
```

### WARNING — permite continuar, notifica
```
verified_at > review_interval
Guía sin FAQ
content_type: experience sin trip_done
Primera persona en contexto no confirmado
```

## 15. `scripts/validate-content.ts`

Punto de entrada CLI y CI:

```bash
npm run content:validate
```

Ejecuta: load → schema validation → reference validation → content rules

```
exit 0 → sin errores
exit 1 → existe al menos un ERROR
```

Los warnings no rompen el proceso.

## 18. Criterio de éxito del primer checkpoint

No se declara terminado cuando "las carpetas existen". Se declara terminado cuando:

> **La guía real de Islandia puede cargarse, validarse, resolver sus referencias y convertirse en un `CompiledGuide` sin que Astro, Vue, FastAPI ni ninguna capa de presentación participe.**

Y además:

```
❌ place_id inválido              → ERROR, falla
❌ schema inválido                → ERROR, falla
❌ experience{} en not_visited   → ERROR, falla
⚠️ dato con verified_at caducado → WARNING, continúa
✅ guía parcial (días 1-2, 9-12) → válida si cumple schema
```

El resultado esperado de `npm run content:validate`:

```
✔ Guides loaded: 1
✔ Places loaded: 1
✔ Schema valid
✔ References valid
✔ Content rules valid
✔ Compilation successful

Content validation passed.
```
