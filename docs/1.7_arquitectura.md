# BLUEPRINT 1.7 — Arquitectura técnica

> Convierte el modelo de datos 1.6 en una arquitectura implementable, mantenible y compatible con todos los outputs de Solo Haz la Maleta.
>
> **Principio rector:** el contenido editorial se escribe una vez y el sistema se encarga de validarlo, transformarlo y publicarlo en diferentes formatos.
>
> La arquitectura debe poder crecer hasta `Mi viaje` y la automatización sin obligar a construir desde el principio una aplicación compleja.
>
> Fuente de autoridad: Documento Maestro + Blueprints 1.5 y 1.6. Este documento los convierte en especificación técnica, no los contradice.

---

## 1. Principios arquitectónicos

### A1 — El contenido manda

```
CONTENT → VALIDATE → COMPILE → OUTPUTS
```

Nunca al revés. El PDF no tiene información que la web no tenga. Mi viaje no inventa información. El componente Vue no tiene datos de Roma hardcodeados. n8n no publica contenido sin revisión.

### A2 — Separar contenido, datos globales y lógica

```
CONTENT DATA          GLOBAL DATA           ENGINES              OUTPUTS
Guías / variantes     Lugares / afiliados   Validator            Web
Días / paradas        Datos verificables    Compiler             PDF
Criterios                                   Budget calculator    Maps
Adaptación                                  Adaptation engine    Mi viaje
```

### A3 — Domain / Presentation

La lógica de negocio nunca vive en Astro ni en Vue. Los componentes son presentacionales: reciben datos y deciden cómo representarlos visualmente. La misma lógica de dominio alimenta web, PDF, mapa y Mi viaje.

```
DOMAIN                    PRESENTATION
Guide / Place             Astro (web)
Variant / Budget          Vue (interactividad)
Adaptation                PDF renderer
calculations              Maps renderer
```

### A4 — Un solo validador

No habrá un validador para Cloudflare y otro para FastAPI. La lógica de dominio es un paquete TypeScript independiente que comparten ambos entornos. FastAPI lo invoca como proceso; el build de Astro lo importa directamente.

### A5 — Git como control editorial

El contenido se versiona. Cada cambio tiene autor, fecha y motivo. Los `verified_at` se actualizan en commits auditables. No hay CMS, no hay base de datos para contenido editorial.

## 2. Stack técnico (decisiones cerradas)

| Capa | Tecnología | Motivo |
|---|---|---|
| Web | Astro 5 | HTML estático, SEO nativo, islas Vue |
| Interactividad | Vue (islas) | Solo donde hay interacción real |
| Estilos | Tailwind | Utilidades, sin CSS custom innecesario |
| Lenguaje | TypeScript | Tipos en todo el dominio |
| Formato editorial | YAML | Legible, comentable, editable sin tocar código |
| Schemas / validación | Zod (paquete TS compartido) | Un solo contrato ejecutable en todos los entornos |
| Hosting web | Cloudflare Pages | Gratuito, CDN global, integración CI |
| Motor dinámico | FastAPI (VPS) | Reutilizado de Reel2Trips |
| Automatización | n8n (VPS, Docker) | Ya en uso |
| Base de datos | Supabase | Ya en uso; para respuestas y compras, no para contenido |
| Email | Desacoplado (ver P15) | MailerLite o Brevo, pendiente de elección |
| PDF | Playwright desde `/print/` | HTML → PDF desde la misma fuente |
| Mapa web | Leaflet | Control visual, filtro por día y variante |
| Navegación | Google Maps URL | Generada desde coordenadas, no construida |
| Exportación | KML | Descargable desde las coordenadas de las paradas |
| CI/CD | GitHub Actions | Build, validación y deploy automático |

## 4. Formato YAML editorial

El autor trabaja siempre con YAML. El sistema lo parsea, valida y transforma.

```yaml
# content/guides/islandia/islandia-en-camper-13-dias.yaml

slug: islandia-en-camper-13-dias
destination: islandia
type: itinerary
content_type: experience
status: draft                    # draft | reviewed | published | archived
trip_done: "2024-08"            # solo cuando content_type: experience

title: "Islandia en camper: ruta de 13 días por la Ring Road"
description: "..."
updated_at: 2026-09-30
cover_image: /images/islandia/diamond-beach-camper.jpg
days: 13

variants:
  - id: intensivo
    name: "Ruta completa"
    days:
      - day: 1
        title: "Círculo Dorado"
        stops:
          - place_id: thingvellir
            order: 1
            duration_min: 70
            planning_status: required
            visit_status: visited
            experience:                    # solo cuando visit_status: visited
              visited_at: "2024-08"
              actual_price_paid:
                amount: 0
                currency: EUR
                notes: "Entrada gratuita; parking de pago"
```

JSON nunca es la fuente editorial. El pipeline es:

```
YAML → parse → Zod validate → compiled object → JSON interno → outputs
```

## 5. Campos añadidos al modelo 1.6

### 5.1 GUÍA — campo `status`

```yaml
status: draft | reviewed | published | archived
```

| Valor | Significado |
|---|---|
| `draft` | En elaboración; no pasa el build de producción |
| `reviewed` | Revisado por el autor; listo para publicar |
| `published` | Visible en producción |
| `archived` | Retirada sin borrar; conserva el historial |

**Regla:** solo las guías con `status: published` aparecen en la web. El CI bloquea si una guía con `status: draft` intenta colarse en el build de producción.

### 5.2 LUGAR — campo `review_interval`

```yaml
review_interval: 6    # meses hasta que se genera warning de verificación caducada
                      # default: 12 si no se declara
```

Los precios de entrada de temporada alta: 6 meses. Las coordenadas geográficas: 120 meses o sin límite. El CI mensual detecta los `verified_at` que superan su `review_interval` y genera una notificación.

### 5.3 PARADA — objeto `experience`

```yaml
experience:
  visited_at: "2024-08"
  actual_price_paid:
    amount: 900
    currency: ISK
    notes: "Precio pagado en agosto 2024"
```

**Solo permitido cuando `visit_status: visited`.** El compilador rechaza `experience` en paradas con cualquier otro `visit_status`.

Esto implementa I16: el precio histórico vive en PARADA, el precio actual verificado vive en LUGAR. Permite mostrar:

> "En nuestro viaje de agosto de 2024 pagamos 900 ISK."

sin afirmar que ese es el precio actual.

## 7. Sistema de errores y warnings

### ERROR — bloquea build y publicación

```
place_id inexistente
affiliate_id inexistente
slug duplicado
variant.id duplicado
campo R ausente
tipo incorrecto
budget basis inválido
visit_status inválido
planning_status inválido
experience en parada con visit_status != visited
status: draft en build de producción
```

### WARNING — permite continuar, notifica

```
Lugar sin source_url
verified_at > review_interval (configurable, default 12 meses)
Guía sin FAQ
Guía con content_type: experience sin trip_done
Guía sin criterio editorial (our_criteria vacío)
Primera persona detectada en LUGAR.notes o PARADA.variant_note con visit_status != visited
```

**Regla sobre primera persona:**
- `LUGAR.notes`: primera persona → warning siempre (los datos de LUGAR son objetivos)
- `PARADA.variant_note` con `visit_status != visited`: primera persona → warning
- `PARADA.variant_note` con `visit_status: visited`: primera persona → permitido
- `GUÍA.our_criteria`: primera persona → **solo informativo**, nunca bloqueante (el criterio editorial sobre lugares no visitados es legítimo: "Kerið estaba en el plan y no fuimos; nuestra valoración es...")

## 9. Dónde corre el compilador

### Build de Cloudflare (web estática)

```
git push → GitHub Actions → Astro build
    │
    └── engine/ (TypeScript)
         ├── parse YAML
         ├── Zod validation
         ├── reference validation
         ├── derived data
         └── content rules
              │
              ▼
         Astro pages (HTML estático)
```

### VPS — FastAPI (operaciones dinámicas)

El mismo paquete de dominio (`engine/`) se invoca para:

```
POST /api/adaptation    ← motor de adaptación
POST /api/purchase      ← compra de Mi viaje
GET  /api/output/:id    ← recuperar output generado
POST /api/pdf           ← generar PDF desde Playwright
```

FastAPI no reimplementa el cálculo del presupuesto ni la lógica de adaptación. Los importa del mismo engine TypeScript (ejecutado como proceso Node.js llamado desde Python, o con un adaptador).

**Un solo dominio. Dos entornos de ejecución.**

## 10. Componentes presentacionales

Los componentes no conocen el destino. Reciben datos y los representan.

```
<StopCard stop={stop} place={place} />
```

Funciona igual para Roma, Islandia, Mallorca y Tailandia.

**Nunca:**

```js
if (destination === 'islandia') { ... }
```

La lógica condicional pertenece al engine o al contenido, nunca al componente.

### Sistema de verificación visual

```
<VerificationBadge type="lived" date="2024-08" />
<VerificationBadge type="verified" date="2026-09" />
<VerificationBadge type="estimated" date="2026-09" />
```

Un único componente con tres representaciones. Los emojis o iconos no están hardcodeados por la aplicación.

## 11. Motor de adaptación

Recibe:

```ts
{
  guide: CompiledGuide,
  group_type: GroupType,
  pace: Pace,
  priorities: Priority[],
  budget: BudgetLevel
}
```

Devuelve:

```ts
{
  recommended_variant: VariantId,
  notes_applied: NoteId[],
  selected_places: PlaceId[],
  filtered_accommodation_zones: Zone[]
}
```

**No genera texto.** Lee los textos editoriales del fichero de guía por ID. Nunca llama a un LLM para inventar una recomendación.

---

## 12. Motor de presupuesto

Función pura. Recibe el presupuesto base, la variante seleccionada y los parámetros del usuario.

```
para cada item:
  if basis = per_person:  coste = amount × n_travelers
  if basis = per_room:    coste = amount × ceil(n_travelers / travelers_per_room)
  if basis = per_group:   coste = amount

total = sum(costes base) + sum(budget_delta.items de la variante)
per_person = total / n_travelers
```

No decide cuánto cuesta nada. Solo aplica las reglas declaradas en el dato.

## 17. Tests mínimos del dominio

No cientos de tests desde el día uno. Solo los que cubren los invariantes críticos.

### Referencias

```
place_id inválido → ERROR de compilación
affiliate_id inválido → ERROR de compilación
```

### Derivados

```
3 paradas → n_stops_total = 3
```

### Presupuesto

```
2 personas, per_person 100 € → total 200 €
3 personas, per_room 200 €, travelers_per_room 2 → total 400 €
```

### Experiencia (I14)

```
visit_status: visited → experience{} permitido
visit_status: not_visited → experience{} → ERROR
visit_status: visited → primera persona en variant_note → OK
visit_status: unknown → primera persona → WARNING
```

### Adaptación

```
group_type: parents → notes de padres aplicadas
budget: ajustado → notes de presupuesto aplicadas
conditions AND: ambas condiciones deben cumplirse
```
